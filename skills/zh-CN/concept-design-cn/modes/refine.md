# 精炼

1. 从需求、规格与相关代码明确失败场景。
   检查受影响概念、规则、调用方和测试。
2. 按根因比较手法，包含不改选项。
3. 记录备选、收益、代价、契约影响与行为差异。
   已确认的新行为先写规格，再实现。
4. 授权的代码修复遵循[实现](build.md)，并验证不变量、目的、受影响场景与失败路径。
   报告保留与有意改变的行为、回归问题和未知项。

| 手法 | 选择与权衡 |
| --- | --- |
| 拆分/合并 | 拆开一个概念或合并不同概念；权衡简单性、能力与控制。 |
| 统一/特化 | 合并变体或保留专门概念；权衡通用性与实际适用性。 |
| 收紧/放松 | 增加或放松同步；权衡自动化与手动控制。 |

规模、名称、共享字段或流程长度本身 MUST NOT 决定手法。
特化只有排除必需行为时才构成缺陷。
区分保持行为的重构与重新设计。
