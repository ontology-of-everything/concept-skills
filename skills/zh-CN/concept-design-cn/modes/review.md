# 审查

MUST 全程只读。
无代码只审设计；无规格时，结论限于有证据的代码性质。
判差异前记录范围、版本、契约确认/覆盖和未知项。

1. 按[资格判据](../references/concept-criteria.md)核对实际用户，API 程序员也是用户。
2. 有代码时，检查[工程架构](../references/architecture.md#审查与验证)。有适用的行为契约时，再应用[漂移检查与严重度](../references/drift-checks.md)。
3. 经规则、实际组合/适配器追踪必需成功与拒绝。
   对照[执行约束及公共检查](../references/execution.md#执行约束)，核对匹配、绑定来源/基数、发生记录/对象/请求隔离与结果。
4. 核对共同效果的隐藏顺序、不变量检查错位、权限过时和禁止的重放效果。
   要求持久化时，检查状态提交 → 完成记录 → 分发的崩溃窗口。
5. 对照具体场景检查必需进展、循环、欠同步、失去用户控制及概念目的偏离。
   协调状态出现独立业务目的/生命周期时，可能需要概念。
6. 指定子集逐个查有需求依据的依赖、入口、规则、资源和构建支持。
   核对引用与图，合并共同根因。

欠/过同步和目的落空须有反例。
查完全部支持入口才能判死规则。
无环动作发生图不证明终止。
类型环、缺深度上限、流程长、规则分散、后台无 HTTP 响应或持久日志本身不是缺陷。
结果可按契约响应、重试、补偿或有意忽略；不要求每输出一条错误规则。

分别报告目的达成、独立性、组合、工程架构、行为漂移和指定子集。
每条发现说明场景、当前证据、失败契约/前提、影响和修复。
