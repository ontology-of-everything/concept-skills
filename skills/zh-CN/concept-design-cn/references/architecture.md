# 工程架构

概念与同步规则语义沿用 Meng 与 Jackson；以下工程命名与布局是本技能的约定。新项目默认同进程多模块单体，采用语言原生源码布局。变更下列职责与依赖边界须显式确认并记录范围。

## 设计与工程术语

| 设计术语 | 工程表达 | 职责 |
| --- | --- | --- |
| 概念 | `modules/<业务名>` 业务模块 | 独立拥有状态、动作与不变量 |
| 概念组合 | `usecases/<业务分组>` 用例组 | 组织应用特有的跨模块协作 |
| 同步规则 | 具名用例、内部方法或事件处理器 | 实现 `when/where/then` 因果规则 |

规格继续使用“概念、组合、同步规则”及 `CONCEPT.md/SYNCS.md`。工程改名保持模型与行为。`modules` 指业务模块集合，不等同于框架发现的全部技术模块，不要求拆成独立构建或部署单元。

## 目录与命名

```text
<源码根>/
  entry/<业务分组>/                 # HTTP、协议、事件、定时任务等入站适配器
  usecases/<业务分组>/
    SYNCS.md                       # 采用相邻布局时
    <动作>UseCase                  # 公开入口规则
    <动作>On<事件>                 # 后续事件规则
  modules/<业务名>/                 # 每个概念独占业务源码包或模块
    CONCEPT.md                     # 采用相邻布局时
    api/                           # 程序内公开命令、查询和值类型
    application/                   # 动作、查询实现及内部端口
    domain/                        # 状态、不变量、领域行为、仓储契约
    adapters/                      # 端口实现、持久化、概念装配
  adapters/                        # 应用级出站适配器，按需
  contracts/                       # 应用级交换契约，按需
  infrastructure/                  # 技术机制，按需
  bootstrap/                       # 最终装配与启动
```

- 新项目采用上述工程名称；既有项目先登记设计与实现映射，在授权范围内改名。业务目录用小写单数；`modules/usecases/contracts` 等集合或角色目录保留固定名称。模块与对应概念、用例组与对应组合沿用业务词根；两类分组不要求彼此同名。Java 包名复合词连写，如 `operatorsession`。类型主体用单数，列表动作和集合变量按语义用复数，如 `ReadBookingsUseCase`、`bookings`。
- 用例组内不再套领域分层。规则可共用源码模块或构建单元。函数式实现保留同等角色与可见性。`ports` 归使用方定义，`support` 限于所属用例组的内部协作者；局部 `contracts` 归交换使用方。额外业务或技术包按真实职责保留或增设，并登记依赖边界。
- Java/Spring 按需显式装配，分别在模块的 `adapters/`、用例组、`bootstrap/` 放置 `<Business>Configuration`、`<BusinessScope>Configuration`、`<Application>Configuration`；既有模块专属装配入口可保留位置。集合装配按工程角色命名，如 `ModulesConfiguration`。在使用方边界用 `<Capability>Properties` 绑定配置。其他语言采用原生等价形式。

## 分层职责与依赖

- **入站适配器 → 公开的 `<动作>UseCase` → 业务模块 API。** 入口负责协议解析、格式校验、可信上下文和响应转换。纯转发 Facade 并入用例入口。应用级出站适配器实现用例端口，默认放顶层 `adapters/`；既有 `entry` 中的出站实现按确认边界保留并注明职责，职责迁移另列范围。
- **业务模块实现独立概念。** 各自拥有状态与不变量。禁止概念互依、互调、互读，以及依赖入口、组合或最终装配。外部身份用类型参数或不透明 ID。
- **业务模块内部。** `api`、`domain` 不依赖其他层。 `application` 依赖 `api`、`domain` 与内部端口。 `adapters` 实现端口，仓储存取聚合，查询端口读取投影。每项职责一个端口。
- **用例实现组合与同步。** 只经业务模块 API 访问概念，依赖所需内向端口，禁止依赖入口或最终装配。业务分支、授权复核、事务和失败策略留在规则中。辅助组件只复用计算或执行机制，不反调规则。组合可保留执行记录，概念业务事实由概念持有。
- **技术边界。** 业务契约及 `api/application/domain` 隔离协议、框架和持久化类型。仅装配代码构造与注入组件，业务代码不查容器。技术库不依赖或协调业务。应用级 `contracts` 定义交换边界，不拥有业务事实；`infrastructure` 提供技术机制，业务分支仍归用例或模块。

## 同步边界

入站适配器建立或传递根动作完成记录及其 flow。每条同步规则对应一个具名实现。每个公开用例实现一条入口规则。规则按 `when` 匹配完成记录、按可选的 `where` 求值、按 `then` 调用动作。同事务后续规则可用内部方法。跨入口复用、独立调度或独立恢复的规则用 `<动作>On<事件>`。后续规则按各自匹配的完成记录触发。事务、因果、原子认领及恢复遵循契约和[执行与恢复](execution.md)。

## 规格归属

规格可与实现相邻，分别位于业务模块的 `CONCEPT.md` 和用例组的 `SYNCS.md`；已有独立设计目录继续保留。未建模块时，放在 `docs/prd/` 下对应的 `concepts/<概念名>/` 或 `compositions/<业务分组>/`。独立布局显式维护以下映射；概念名、实例及类型绑定和规则身份继续沿用设计定义：

```text
<设计根>/concepts/<概念名>/CONCEPT.md → <源码根>/modules/<业务名>/
<设计根>/compositions/<业务分组>/SYNCS.md → <源码根>/usecases/<业务分组>/
```

总体 PRD 索引权威规格，验收关联契约或场景。每份规格只有一处维护正文，相邻与独立布局不重复维护。已确认位置的迁移须经授权。

实例、类型绑定与共用入口契约各声明一次，重复 include 仍指向同一实例。`SYNCS.md` 逐条映射到用例、内部方法或事件处理入口。规格、测试和运行记录使用同一规则身份，迁移保留持久身份及触发、事务、失败和重试语义。`// flow:` 仅用于文档分组。

## 审查与验证

常规检查或 CI 覆盖实际源码、构建单元与配置。核对目录、命名、模块发现、设计到实现的映射和依赖图，检查可见性、环、类型泄漏及适配器装配。检查器显式区分设计与源码路径，业务模块互依、互调、互读仍判违规。违规报位置并失败，漏检或未解析依赖记为缺口。行为测试覆盖触发、事务、失败、重试与并发。

工程改名同时核对源码与测试路径、import/导出、构建清单、框架模块标识及接口、架构检查匹配、装配与扫描、配置完整类名和文档链接。持久事件、序列化类型与恢复记录中的名称须先检查存量及发布状态，再明确迁移或兼容范围；未发布系统按确认的首发契约处理。运行受影响的架构检查、编译和行为回归，确认规则触发、事务和恢复语义保持不变。
