# 重建规格

从实际代码重建有证据的候选基线，再确认哪些使用方可依赖它。观察到的行为不自动成为需求：逐项区分**观察、推断目的、已知缺陷、期望修复与已确认要求**，保留证据与确认状态。

## 概念

检查导出、调用方、持久化、结果分支、不变量和测试，按[规格记法](spec-notation.md)记录类型、基数、初态、动作结果和查询。没有可观察效果的私有辅助函数或缓存无需入规格。所需同步另列；概念间耦合记为缺陷，不写成允许的依赖。

## 同步

从应用目的与场景追踪处理器、注册、mediator 和适配器，直到公开动作；按[工程架构](architecture.md)映射实现。直接互调或私有 SQL 不因转录为规则而合法，纯数据转换归 [PIPELINE](pipeline-spec.md)。

逐条核对入口完成记录、结果分支、绑定与调用，以及请求/对象/发生记录的关联。所有分组引用同一份应用实例、类型与入口声明；重复 include 不创建新实例。

完成重建须覆盖：

- 全部 include、签名和调用参数，查询零/多行行为与请求隔离。
- 每个可达结果的响应、重试、补偿或忽略策略；无证据的策略保持未决。
- 部分完成、重放与循环；循环须终止或显式受控继续，深度上限按需设置。
- 有证据的[执行约束](execution.md#执行约束)，以及保留合取、多目标和查询读取的图。

报告规则数、场景覆盖、边界问题和未知项，明确候选基线尚待确认的部分。
