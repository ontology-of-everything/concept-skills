# 概念审查

## 目标

判断概念与应用设计能否兑现目的，已有代码是否符合设计。仅在显式调用 `$concept-review-cn` 时运行，全程只读。
无代码时审设计；无规格时只审可验证的代码性质。

## 原则

全程只读。发现须有已读需求、规格、代码或测试作为依据，推断与缺口另标。
无实现不报告实现违约。运作原理缺少测试是验证缺口，目的论证失败须附反例。

按确认的工程约定检查，将架构偏差与概念缺陷分开，不把新工程结构追溯为旧项目要求。

## 概念

| 维度 | 核对问题 |
| --- | --- |
| 适切性 | 声明前提下的行为能否满足实际需要？ |
| 独立性 | 概念能否独立理解，概念模块之间是否互不引用？ |
| 组合 | 同步是否遵守概念契约，能否支持应用场景？ |
| 漂移 | 实现遗漏或违背了哪些已确认契约？ |
| 产品子集 | 指定子集是否保留目的、入口、规则与资源？ |

概念论证说明契约如何支持运作原理和目的。应用论证说明概念选择与规则如何支持场景和目的。
局部测试通过不证明应用适切。同步可以限制行为，但不能超出概念契约。

## 流程

1. 读[规格契约](references/spec-format.md)、需求、索引和相关规格，记录范围、版本与缺口，再追踪已有代码。
2. 检查目的兑现、单一目的、完整行为、独立性与熟悉性。说明实际用户及价值，API 程序员也是用户，新颖本身不是缺陷。
3. 有代码时按[漂移检查](references/drift-checklist.md)核对接口、状态、不变量、依赖、私有访问、共享状态与协议类型泄漏。
4. 按[组合检查](references/composition-checklist.md)检查合法场景、触发、绑定、隔离、失败、重放、循环、遗漏联动和过度自动化。
5. 逐个核对指定子集的需求依赖、入口、规则、资源与构建支持。对账引用和图，按根因合并发现。

核对定义时读[来源](references/sources.md)。静态推演不证明运行时符合性。

| 正例 | 反例 |
| --- | --- |
| 指出拒付后预约仍被占用，附规则位置与可达路径。 | 只因流程较长，就判定设计有问题。 |

## 报告与完成条件

报告上述维度的范围、覆盖、严重度与未核实项。每条发现说明场景、当前证据位置、失败关系或前提、影响与修复步骤。
Medium 及以上须有规格或代码证据，欠同步与过同步须附具体场景。

模型问题交设计，转录或索引错误交 PRD，代码违约交实现。当前修复与后续依赖分开。
只将已执行检查标为通过，不改规格、代码或历史。
