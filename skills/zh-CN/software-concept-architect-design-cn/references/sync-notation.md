# 组合检查

sync 的写法、flow、失败与重放以 [规格契约](spec-format.md) 为准。这里只判断设计选择。按数据依赖拆规则时对照 [订位例](example-reserving.md)。

## 同步是否合适

- **欠同步**：该发生的联动没有发生。用收紧（tighten）补上规则。
- **过同步**：自动化夺走用户需要的手动控制。用放松（loosen），或改成用户可配置。
- 判断依据是应用目的和具体场景。
- **占位动作**是为了被别的动作同步而预留的动作，例如 access、notify。它仍须有自己的契约。
- **协同**是组合产生的、单个概念没有的价值。若因此改写了概念原来的 purpose，回到资格标准重审。
- 参与者多或 flow 长，只说明场景复杂。重审概念边界要有独立 purpose 和自有业务状态。日志和队列不是概念。

## 同步图

每个 sync 一个规则节点：多个 when 连入，多个 then 连出，where 另标为读取。画成 A→B 时保留规则名，并写明多个 when 是否必须同时成立。这张图不表示产品依赖。

循环要有终止条件，或有受控地一直运行的依据。用工程上限截断时，用户必须能看出已被截断。

## 依赖与子集

- **内在依赖**：概念自己的定义依赖另一个概念。改为类型参数，或改到 sync，不留在概念定义里。
- **外在依赖**：在这个应用里，纳入 A 只有连同 B 才有意义。写在对齐的依赖与子集，记作 `A → B`。转录 PRD 时放入总体 PRD。
- 代码上的耦合不能用来证明产品必须依赖。除了依赖闭包，还要查 purpose、入口、剩下的 sync 和外部资源。
- 同一个依赖环里的概念，一起纳入或一起排除。把它们分成一组，本身还不是可交付的子集。
