# 概念规格（concept）

焦点：模块体现什么目的性行为，事实是否支持这份描述？CONCEPT 是行为契约及代码生成上下文，不能代替实现证据。参数、授权和落位遵循入口。

## 定义与约束

- **purpose** 声明单一可评价需要；**OP** 用有区分力的场景解释目的兑现；**state/actions** 定义允许行为。新建时检验两层关系，回填时重建论证并标明推断。
- **独立性** 要求四节不依赖其他概念定义，类型参数只是不假定字段的身份，同名合法。跨概念业务行为写 SYNCS，notes 仅记应用背景。
- **状态所有权** 决定读写边界：外部写入经声明 actions，读取经公开抽象状态或声明 query，概念互不调用、无共享可变状态。组合层调用公开接口。
- **动作声明** 规定可发生的行为，**完成事件** 记录一次实际发生；日志、指标等不因存在事件就成为概念，仍须独立目的与完整行为。

## 契约模板

使用 [统一规格模板](spec-format.md)，按其中的字段、结果分支和旧格式兼容规则核对。

## 从事实到规格

1. 读取导出项、调用点、import/use/require、持久化及失败路径；根据实际需要说明目的，证据不够则标推定。纯编排归 SYNCS，支撑类型/工具不强行建概念。
2. 对照契约推演 OP：动作能否产生结果，结果为何满足需要；列具体反例或未决前提。回填不以理想故事掩盖现状，复杂边界或目的取舍交 software-concept-architect-design-cn。
3. 跨概念私有访问、共享状态、直接 API 互调及多目的逐项附位置报告；纯缓存/索引与辅助函数无可观察影响时不算契约遗漏。
4. 新建/更新补齐已确认的状态、动作与输出；缺口只阻塞相关部分。发现模式仅列候选、purpose 与证据，并提示适用的 pipeline/sync。

## 完成条件

定义、OP 前提及动作/query 可追溯；事实、推断和缺陷分别呈现。耦合写入应用取舍或漂移报告，不补 interactions/dependencies/known coupling 段。所属 PIPELINE 与 CONCEPT 共目录；避免根目录规格笼罩无关模块。hook 的查找/遮蔽行为仅见 [hooks-runtime.md](hooks-runtime.md)。
