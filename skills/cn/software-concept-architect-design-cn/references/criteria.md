# 资格判据

概念是同一个东西的两面：有效使用应用所必须理解的心智构造，以及内聚的功能单元。它由动态行为定义。三个部分是名称、purpose、OP，用用途和用法说明。餐厅订位的 purpose 是确保届时有桌可用，OP 是联系餐厅、提前选定时间并到场。

下列八项每个概念都要满足。后表用来区分其他构造。

## 决策依据

| 判据 | 决策依据 |
| --- | --- |
| 面向用户 | 立为概念的是用户体验到的行为。隐藏结构只作实现支撑。设计 API 时，程序员是用户。 |
| 语义性 | 概念由抽象、语义化的静态结构与动态结构构成。控件、配色、UI 皮肤不是概念。 |
| 独立性 | 不参照其他概念就能理解和使用。评论：选定制品、写下想法、随制品显示。制品可以是帖子、回复或另一条评论，定义不包含它们。必须依赖另一概念则不独立。 |
| 行为性 | 行为通常简单；更复杂的行为留在概念之间的交互。点赞：人们给条目点赞，赞最多的升到排名顶部。池塘（小、静止、水体）这种分类不是概念。 |
| 目的性 | purpose 须用户可理解，且本身带来真实价值。只在更大概念里扮演角色的，不单立为概念。社会保障号码的 purpose 是把养老金与个人关联；「获取社会保障号码」只是其中的角色。 |
| 端到端 | 功能必须走到兑现 purpose。用户认证若有注册账户，就必须有认证动作。OP 若只是「动作发生则状态如此更新」，补上兑现行为。 |
| 熟悉性 | 用户应能不读手册就开始使用。可以有新概念；新颖更多来自旧概念的新组合或细调。帖子、好友/关注、点赞、回复、评论、话题标签在常见社交应用里几乎相同。更好的图片支持、帖子长度限制是变体。 |
| 可复用性 | 先查目的性、端到端和独立性。已经复用不能代替这三项，尚未复用也不能否定。会议标识符让各方无需逐个呼叫即可加入；Zoom 引入后，Google Meet 与 Microsoft Teams 效仿。 |

| 构造 | 决策依据 |
| --- | --- |
| 类 | 通常不面向用户，也很少独立。不立为概念。 |
| 特性 | 「账户可以设为私密」是关注者概念上可选的审批。不另立概念。 |
| 用户故事 | 「记录今天哪些学生出勤」本身不带来价值。概念是考勤：每日录入、期末汇总，或许还有屡次缺勤警告。单条故事不是实现增量。 |
| 微服务 | 服务边界不是概念边界。 |
